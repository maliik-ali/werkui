# WerkUI: project guide

## What this is

WerkUI is a **single, standalone open-source component library** for SaaS and agency landing pages. Model it on Magic UI and Kokonut UI: a docs website where each component has a live preview, the code, an install command and props, distributed through the **shadcn registry**. There is no marketplace and no Figma/Framer/Webflow storefront.

- Owner: Malik Ali (senior product designer, Rayvens Tech). Domain: werkui.com. Free repo is public, MIT.
- Niche: **SaaS and agency landing-page blocks** (heroes, bento grids, pricing, testimonials, FAQ, navbars, footers, CTAs). EdTech is a possible later pack, not now.
- Money, later: **Pro components and paid templates** in a separate private repo under a commercial license. Free templates and components are the marketing. Do not build the paid side until asked.
- Templates are built from the components. When a template needs something missing, build it as a new library component first.

## How to work (the owner's rules)

1. **Code first.** Do not start with a Figma design system. Build each component in code, judge it in the browser, then document it. Figma is only for laying out whole templates, later.
2. **Follow the existing website design.** Do not redesign the site. Reuse its look: tokens in `src/app/globals.css` (brand blue, orange accent), Geist font, rounded-full pills, bordered `bg-card` cards, dotted preview backdrop, light and dark themes. New pages and chrome should match what is already there.
3. **Components follow the Magic UI / Kokonut UI pattern:** copy-paste source, animated and polished, installed with `npx shadcn@latest add https://www.werkui.com/r/<slug>.json`.
4. Recommend, don't survey. Make sensible choices and say what you chose.
5. Never commit, push or deploy unless explicitly asked.

## Layout

```
src/registry/werkui/<slug>.tsx            the component (what users install)
src/registry/werkui/examples/<slug>-demo.tsx   the demo shown on the docs page
registry.json                             installable items (deps, css keyframes)
public/r/*.json                           generated by `npm run registry:build`, committed
src/lib/components-registry.ts            docs metadata: title, category, props, demo
src/app/                                  site: / and /docs (intro, installation, components index, components/[slug])
src/components/site/                      site-only chrome (never imported by registry components)
```

## Component rules

- **Minimal dependencies.** Allowed: `react`, Tailwind v4, `cn` from `@/lib/utils`, `lucide-react`, and `motion` only when animation needs it. Adding anything else needs a stated reason and an entry in `THIRD-PARTY.md`.
- **Self-contained.** A registry component must not import from `src/components/site/` or anything outside `src/registry/werkui/`, `@/lib/utils` and `@/components/ui/*`.
- **Importing another WerkUI component:** use `@/components/ui/<slug>` (where `registry:ui` items install in users' projects), never `@/registry/werkui/...`. `tsconfig.json` maps `@/components/ui/*` to `src/registry/werkui/*` as a fallback so it resolves here. List the other item in `registryDependencies` with its `https://www.werkui.com/r/<slug>.json` URL and in `uses` in `components-registry.ts`. Demos (not shipped) may import from `@/registry/werkui/...`.
- **Theme tokens only.** Use `bg-card`, `text-muted-foreground`, `bg-primary`, `chart-*` and so on, never hard-coded colours, so every component works in light and dark and inherits the user's theme.
- **Props:** extend the root element's props, spread the rest, merge `className` with `cn()`. Document every custom prop in `components-registry.ts`.
- **Accessibility:** semantic elements, visible `focus-visible` styles, respect reduced motion (`motion-reduce:` classes or `useReducedMotion`), no interactive element nested in another (no `<a>` in `<a>`, no `<button>` in `<a>`).
- **Server components by default.** Add `"use client"` only when needed (hooks, motion).
- **Animations** are CSS keyframes defined in `globals.css` (`@theme`) and repeated in `registry.json` so installs get them. Put the token under `cssVars.theme` (e.g. `"animate-marquee": "marquee 40s linear infinite"`) and the keyframes under `css` (`"@keyframes marquee": {...}`). Do NOT put `"@theme inline"` inside `css`: the shadcn CLI fails with `update-css: Unknown word ...`.

## Add a component

1. `src/registry/werkui/<slug>.tsx` and `examples/<slug>-demo.tsx`.
2. Entry in `registry.json` (`dependencies`, `css`, correct `type`: `registry:ui` for primitives, `registry:component` for sections).
3. Entry in `src/lib/components-registry.ts` (slug, title, description, category, file, Demo, props).
4. Add `isNew: true` for fresh components (shows a badge in the sidebar and search). The docs page builds the Manual install steps from `registry.json`, so keep `dependencies` and `css` accurate there.
5. Test the install for real, not just the build: in a throwaway shadcn project run `npx shadcn@latest add /path/to/werkui/public/r/<slug>.json`, then check the files, the CSS in `globals.css`, and that `tsc` passes there.
6. `npm run registry:build`, then `npm run lint`, `npm run typecheck`, `npm run build`. Commit `public/r`.
7. Look at it in the browser, in light and dark, and at phone width.

CI (`.github/workflows/ci.yml`) runs lint, type check, a registry-up-to-date check and the build. Keep it green.

## Next.js 16 gotchas (`cacheComponents` is on)

- Read `node_modules/next/dist/docs/` before writing Next.js code. This is not the Next.js in your training data.
- Awaiting `params` must happen inside a `<Suspense>` boundary (see `src/app/components/[slug]/page.tsx`).
- Uncached `fetch` needs `"use cache"` (see the GitHub stars call in `site-header.tsx`). Syntax highlighting goes through `src/lib/highlight.ts`, which is cached because shiki reads `Date.now()`; never call `codeToHtml` directly in a page.
- Do not export `dynamicParams`. Do not call `Date.now()` or `Math.random()` in server render.
- Read files with statically scoped paths, e.g. `path.join(process.cwd(), "src", "registry", "werkui", name)`.

## Testing in the browser

- Dev server: `preview_start` with `werkui` (port 3001, configured in the parent folder's `.claude/launch.json`).
- If the browser pane is hidden, animations do not run and `motion` elements stay at `opacity: 0`. That is not a bug. Force them visible with a script to check layout.
- Check the console for hydration errors after changing any page.

## Dependencies and licenses

Everything here is open source (see `THIRD-PARTY.md`). Keep the dependency footprint small, keep `package-lock.json` committed, and do not use "shadcn" in WerkUI's name or branding. "Works with the shadcn CLI" is fine.

## Website

Modelled on magicui.design: top announcement bar, header with search (⌘K) and GitHub stars, a docs area with a left sidebar, breadcrumb with previous/next, Preview/Code tabs with a replay button, CLI/Manual install tabs, Usage, Props, and an "On this page" list. Old `/components` URLs redirect to `/docs/components`. The landing page must not show invented testimonials, logos or numbers as if they were real.

## Deployment

- Live at https://www.werkui.com (the apex `werkui.com` 308-redirects to `www`, so install URLs and `site.url` use `www`). Hosted on Vercel, deployed from `main` of `github.com/maliik-ali/werkui`.
- `vercel.json` (`{ "framework": "nextjs" }`) must stay: the Vercel project relies on it, and without it the deploy serves only static files and every page 404s.
- After a deploy, check `/`, `/docs/components/<slug>`, `/r/<slug>.json`, and run a real `shadcn add https://www.werkui.com/r/<slug>.json` in a throwaway project.
